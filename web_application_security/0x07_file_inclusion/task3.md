# Task 3. Poison the logs

## **Task Description**

The goal remains to capture the flag, but this time it is placed in an unknown location on the server. To succeed, you will need to explore the files accessible through the application and use the available resources strategically to progress step by step.

Target Machine: Cyber - WebSec 0x07 \
Main Endpoint: http://web0x07.hbtn/find_your_shell/ \

1. Try accessing task4_file_hub/shell.php — loading this file is necessary to set the required session variable.
2. Some scripts on the machine cannot be executed directly,  they can still be triggered indirectly once the correct sequence of files has been accessed.

Repo:

GitHub repository: dlh-cyber_security \
Directory: web_application_security/0x07_file_inclusion \
File: 4-flag.txt


## **Solution**



- Start sandbox `cyber_websec_0x07`.
- Start openvpn.
- Put IP address of the sandbox in `/etc/hosts` file.
```bash
echo "10.42.44.147 web0x07.hbtn" | sudo tee -a /etc/hosts
sudo vim /etc/hosts
ping -c 2 web0x07.hbtn
```



Objective: Locate and retrieve `4-flag.txt`, whose filesystem location is unknown.

This challenge introduces two important concepts:

- Local File Inclusion (LFI): Reading or including files from the server's filesystem.
- Log poisoning: Placing controlled content into a server log and potentially executing it through a vulnerable file-inclusion mechanism.

The hint also suggests that accessing `task4_file_hub/shell.php` sets a session variable needed for subsequent steps.

Excellent. Restarting the server gives us a clean access log, and you've confirmed that `FLAG_SET` is initialized.

`ffuf` could be used to brute-force the filenames, but we now have a more direct option: **use log poisoning to execute PHP's **`scandir()`** function and list the directory contents.**

Our earlier payload likely failed because Nginx escaped its double quotes, producing invalid PHP. This time we'll use single quotes.

#### **Execute:**


The injected PHP is:

```php
<?php
echo 'DIRLIST_START';
print_r(scandir('task4_file_hub'));
echo 'DIRLIST_END';
?>
```

1. Nginx records our PHP payload in `/var/log/nginx/access.log`.

4. We should obtain the filenames in that directory.

**Expected response for this step:** `HTTP/1.1 200 OK` with the normal homepage. The PHP payload won't execute until we include the access log.

### **Step 24: Inspect the raw log-inclusion response**

The command returned no output, but that **doesn't necessarily mean the PHP injection failed**.

Our previous command used:

```
grep -oP 'DIRLIST_START.*?DIRLIST_END'
```

The problem is that `print_r(scandir(...))` produces multiline output, while `grep` normally matches one line at a time. Therefore, it may miss a successful directory listing.

Let's inspect the response directly.

**Execute:**

```bash
curl -sS \
  -b task3.cookies \
  -c task3.cookies \
  'http://web0x07.hbtn/find_your_shell/find_your_shell.php?filename=/var/log/nginx/access.log' \
  | tail -c 3000
```

**What we're looking for:**

1. `DIRLIST_START`**followed by**`Array (...)`**:** Our PHP payload executed successfully and returned a directory listing.
2. **Output ending at**`<?php`**:** The injected code may have caused a PHP parsing or execution error.
3. **Normal log entries without our marker:** We need to investigate whether the payload was recorded.
4. `File not found!`**:** The log is no longer accessible at the specified path.
